# 作战台账：把状态从记忆里搬到文件里

> 🔷 Pro Lab 方法论卡（架构推导，非语料回灌）—— 尚未经 Pro Lab 实战检验

## 触发信号 / 适用处境

- 已知主机 > 3 台，或存在 > 1 个网段
- **第二次开工**（隔夜回来），说不清"控了谁、有什么凭据、哪条隧道通哪"
- 刚拿到一个**不知道能干什么**的东西（ticket / 证书 / hash / ACL 缺陷）

## 前置准备

```bash
mkdir -p ~/eng/creds && cd ~/eng && git init -q && $EDITOR ledger.md
# 两个入口动作,不做"整理": 开工读 §5 未决队列取活;收工把「我知道什么/下一步试什么」写进 §5
# 凭据落文件(见 ad-checklist 凭据管理段): C1→creds/C1.txt  C2→C2.nthash  C3→C3.ccache
```

🔴 本卡只管**状态放在哪**。凭据去哪找 → `credential-hunting-locations`；怎么验 → `credential-spraying-password-reuse`；验完怎么打 → `lateral-movement`。**本卡不重复它们。**

## 模式 1: 三条互相独立的轴（独立的原因 = 更新频率与失效方式不同）

| 轴 | 记什么 | 为什么会变 |
|---|---|---|
| **资产轴** | 主机 / IP / OS / 角色 / 是否已控 / 权限 / 端口 / 服务 / **在哪个网段** | 状态会变:你控了它、它重启了、它被别人重置了 |
| **凭据轴** | 凭据值 / **类型**(明文 / NT hash / ticket / 证书 / SSH key) / 来源 / **已验证可用于哪些主机** / **还没试过哪些** | 会失效:改密、票据过期、证书吊销 |
| **网络轴** | 网段 / 各段可达性 / **隧道拓扑(谁穿谁)** / 每段有哪些主机 | 会变:新隧道建立、旧隧道断、跳板掉线 |

🔷 **为什么必须独立**：三者**失效方式不同** —— 资产轴因"机器状态变化"、凭据轴因"凭据被改/过期"、网络轴因"隧道断"，**更新时机也不同**（资产=拿下/失去主机；凭据=拿到当下；网络=建/断隧道）。合成一张表后，任何一处小变化都要重写整行 → 人就不写了 → 台账腐烂成过期文档。分开只多两张表头，换来每一轴能被单独、廉价地更新；三轴的状态性质也不同（事实 / 实验结论 / 条件性事实），混在一行就分不清"我没试"和"我试了不行"。

## 模式 2: 🔴 第四栏 依赖链 —— 最容易被忽略、但最值钱的一栏

格式：`要达成 X ←需要先有— Y`。**为什么它最值钱**：拿到 **Y** 的那一刻，台账会立刻告诉你 **X 解锁了**。没有这一栏，Y 到手你也不知道它有什么用 —— 于是 Y 静静躺在笔记里，而你还在为 X 发愁。

```
每入账一条新东西(凭据/主机/隧道/ACL 缺陷),立刻问:「这条解锁了哪条 X?」
  答得出 → X 行状态 ❌ 改 ⏳,写进未决队列    答不出 → 新建 X = "未知用途",状态 "待定"
```

## 模式 3: 第五栏 未决队列（open leads）

🔴 **每次开工只从队列取活，不从「我想干什么」取活。** 队列是**唯一的 session 间接口**。每条 lead 只记三个字段（多写就不会写）：

| 字段 | 要求 | 反例 |
|---|---|---|
| **假设** | 一句**可证伪**的话 | ❌"看看 DC" ✅"C1 能在 B 段 DB01 复用" |
| **预计代价** | 时间盒(如 45min)，到点无条件回队列重排 | ❌"需要一些时间" |
| **期望产出** | **能力类别升级**之一(新网段 / 新域 / 新凭据类型 / 权限升级)，或**一条新 lead** | ❌"了解更多信息" |

取活顺序（🔷）：**最便宜的假设先验** —— 凭据复用 < 已知漏洞 < 配置缺陷 < 服务攻击 < 自定义利用。

## 模式 4: 凭据-主机匹配矩阵（N×M 问题）

N 个凭据 × M 台主机时，裸喷洒既慢又吵，但不喷会漏。🔷 **先按「凭据来源」推断适用面，再定向验证**：

| 凭据来源 | 推断适用面 |
|---|---|
| 本地账号(某机 SAM/影子文件来的) | **只适用本机**(除非本地管理员复用) |
| 域账号 | **全域适用** —— 先看登录限制(Protected Users / 登录时段 / 工作站限制) |
| 服务账号 | 认证面：通常只对**特定服务**有效(MSSQL / IIS / 计划任务)；🔴 但它的**出网认证身份**可能是**机器账号**(域成员) → 虽不是域用户凭据，却足以做域枚举 |
| 机器账号 | 认证面：本机 + 特定委派场景；🔴 权限面：它是域成员、对 AD 有默认读权限（"只有本机管理员"时可当域枚举跳板） |
| 证书 / ticket | 看证书模板的 EKU 和票据的 SPN |

→ **先按表缩小到 2–3 台，再验证**：比全喷快、比不喷可靠。矩阵落到台账里就是一张表 —— 行=凭据、列=主机、格=三态：⬜ 未验证 / ✅ 已验证可用 / ❌ 已验证失效，三者必须区分。**⬜ 堆积 = 你在收集，不是在推进。**（标"已验证失效"前先排除假阴性：隧道半死、cwd 不对都会伪造失败 → `blocking-points-detail`。）

## 模式 4.5: 🔴 台账里「已验证」与「推测」必须视觉上可区分

**判据（一条就能查）**：随便指台账里的一行，能不能**在 1 秒内**说出它是事实还是推断？

```
[ ] 🔴 每条结论**强制前缀**：`[已验证]`（有命令输出/文件字节为证） / `[推测]`（由旁证推断）
[ ] 🔴 `[推测]` 项必须带两样：**依据**（哪条观察推出它）+ **否证方式**（怎么一步证伪）
[ ] 🔴 禁止裸陈述：既不标 `[已验证]` 也不标 `[推测]` 的行 = 违规行
[ ] 收尾时把所有 `[推测]` 拉成一张清单 → 这是 retester 的输入（不是"存疑留档"）
```

> 🔴 实测代价（小但真实）：把从日志文件名事件推断的 `root.txt` **写成了事实**，
> 实际路径是 `master.txt`（取旗时 `STATUS_OBJECT_NAME_NOT_FOUND`）。
> 代价只是一次失败取旗 + 一次纠正，但它暴露的是**推断与事实在台账里同权呈现**——
> 而下一个 agent 无法区分"这条我验过"和"这条我猜的"，于是**会拿推断当地基继续往上盖**。

## 模式 5: 台账的自我诊断（无 oracle 环境下的自制 oracle）

| 信号 | 读法 | 动作 |
|---|---|---|
| 未决队列**变短** | 🔴 危险信号:快没路可走了 | 停下活,回三轴重扫(新端口/新用户/新共享) |
| 未决队列**变长** | 好信号:在产生新信息 | 保持当前线 |
| 凭据矩阵**已验证覆盖率在涨** | ✅ 在推进(最可靠的进展指标) | 继续 |
| 矩阵里 ⬜ 长期不降 | 你在收集而不是在使用 | 下一轮只做验证,不做发现 |
| 依赖链**连续多轮不变长** | 🔷 大概率是死树 | 回队列取最便宜的替代 lead |

🔷 **每半天问一次**：「如果我是出题人，这个 lab 的预期路径是什么形状？」—— 对照台账；不吻合往往意味着走进了非预期路径。

```markdown
# 作战台账 — <engagement> · 最后更新 <YYYY-MM-DD HH:MM>

## 1. 资产轴
| 主机 | IP | 网段 | OS | 角色 | 已控 | 权限 | 关键端口/服务 | 备注 |
|---|---|---|---|---|---|---|---|---|
| WEB01 | 10.10.10.5 | A | Ubuntu22 | 边界 Web | ✅ | www-data | 80,22 | 双网卡→B 段 |
| DC01 | 10.10.10.10 | A | Win2019 | DC | ❌ | — | 88,389,445 | 域 dom.local |

## 2. 凭据轴
| ID | 值/引用 | 类型 | 来源 | 已验证可用 | 已验证失效 | 还没试过 |
|---|---|---|---|---|---|---|
| C1 | creds/C1.txt | 明文 | /var/www/.env @WEB01 | ssh WEB01 | — | B 段全部, WEB01 提权 |
| C2 | creds/C2.nthash | NT hash | SAM @WEB01 | — | smb DC01 | WEB01, DB01 |

## 3. 网络轴
| 段 | CIDR | 可达 | 经谁可达 | 隧道(谁穿谁) | 段内已知主机 |
|---|---|---|---|---|---|
| A | 10.10.10.0/24 | ✅ 直连 | — | — | WEB01, DC01 |
| B | 172.16.1.0/24 | ✅ | WEB01 | chisel R:socks 1080 | DB01(待枚举) |

## 4. 依赖链
| 要达成 X | 需要先有 Y | Y 状态 | 解锁后动作 |
|---|---|---|---|
| DCSync | DC 上具复制权限的账号 | ❌ 无 | — |
| B 段横向 | 任一在 B 段可用的凭据 | ⏳ C1 待验 | 先验 1 台 |

## 5. 未决队列（开工只从这里取活）
| # | 假设 | 代价盒 | 期望产出 | 状态 |
|---|---|---|---|---|
| L1 | C1 可在 B 段 DB01 复用 | 20min | 新网段立足(能力升级) | 待做 |
| L2 | WEB01 提权面在 sudo -l 输出里 | 30min | 权限升级 | 待做 |

## 6. 事实与推断（🔴 每条结论强制前缀，禁裸陈述）
| 前缀 | 结论 | 依据 | 否证方式 |
|---|---|---|---|
| [已验证] | WEB01 是双网卡，可进 B 段 | `ip a` 输出见 `traces/A1.md:12` | — |
| [推测] | DC01 的旗在 `root.txt` | 由 2024 构建期文件事件推断（只有它没改名） | 直接 `--get-file` 试一次，返回 `STATUS_OBJECT_NAME_NOT_FOUND` 即推翻 |
```

## 快速检查清单

```bash
[ ] 三条轴是分开的表(没有合成一张大表)?
[ ] 每条新入账的东西都问过「解锁了哪条 X」?
[ ] 凭据三态(未验证/已验证可用/已验证失效)分开了?
[ ] 未决队列每条都有 假设+代价盒+期望产出?
[ ] 🔴 台账里有没有**裸陈述**（既没标 [已验证] 也没标 [推测]）? 推测项有没有写「依据 + 否证方式」?
```

## 教训

1. 🔷 **瓶颈是状态管理,不是技巧** —— 你的对手是自己的记忆。人脑工作记忆约 7 项,30 台 × N 凭据 × M 网段必然溢出；"拿到 shell" ≠ 进展,真进展是**能力类别升级**。
2. 🔴 **即时写,不批量写** —— 拿到凭据的当下就写,攒着晚上整理一定会漏。
3. 🔴 **依赖链是唯一会"主动解锁"的栏目** —— 只有它会在你拿到 Y 时提醒你"现在能干什么"。
